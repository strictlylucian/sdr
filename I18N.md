# Documentation internationalisation

Internationalisation belongs to the consuming application. Neither `@strictlylucian/sdr-core` nor `@strictlylucian/sdr-react` includes dictionaries, an i18n runtime, locale selection or date/currency formatting helpers. The library displays supplied content and accepts callbacks where content changes with state.

## Component contract

- `SdrProvider` scopes theme, density and styles. Its standard `lang` attribute describes content for browsers and assistive technology; it does not select translations. Any language tag is accepted.
- Labels, hints, errors, headings, navigation text and accessible names are supplied through props or HTML markup. Compound controls require their own labels: password show/hide, accordion expand/collapse, date parts, modal close and navigation menu.
- `CharacterCount` requires an application `formatCount(remaining)` callback. A negative value means the limit has been exceeded. The application chooses wording, plurals and number formatting.
- Portable HTML passes `formatCount(remaining, root)` through `SDR.init(root, options)`. Password and accordion action labels come from their documented data attributes. No language is inferred from `lang`.
- Text-table collation can be supplied through `compareText`; numeric columns compare numeric values. There is no built-in collation locale.
- Updating supplied labels or formatters preserves answers, password visibility and expanded sections. Missing required enhancement labels or count formatters fail rather than selecting default copy.

A consuming app can use i18next, FormatJS, another translation library or plain strings. No SDR translation provider or locale JSON export is required. Dates and currency can use the app's own `Intl` formatters.

## Documentation runtime

The documentation uses [i18next](https://www.i18next.com/) for UI and example translations. It is a dependency of `@strictlylucian/sdr-docs` only. Astro Starlight supplies language routing and its own framework translations.

The docs create one synchronously initialised instance with local resources and obtain a language-fixed translator per call. Concurrent Romanian/English server rendering does not change global language state. There is no language detection, translation backend or remote resource request. Missing keys and interpolation values throw; there is no cross-language fallback in project dictionaries. Romanian/English character-count examples use i18next's plural support.

Starlight overrides are intentionally partial; the framework provides its remaining built-in locale strings. Catalogue metadata remains typed JSON data, rather than runtime translations shipped to library consumers. Stable IDs, canonical parent slugs and variant anchors keep routes independent of visible names.

## Build and verification

`npm run build` regenerates localised docs, examples and readable public snippets. i18next is bundled with documentation example wiring, never into `sdr.js`. The portable library remains exactly `sdr.css` and `sdr.js` with no translation assets or requests.

Tests cover documentation dictionary/placeholder/plural parity, missing-copy failures and interleaved languages. Component tests pass their own strings and formatters, including French/German copy and changes without lost state. Package checks reject translation modules or i18next dependencies in both library archives. Browser tests exercise the Romanian/English docs and examples.
